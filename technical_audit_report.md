# Технічний аудит бекенду FERP (Family ERP)

Цей звіт містить глибокий аналіз архітектури, стабільності та готовності системи до масштабування та впровадження Local-First синхронізації.

---

### 1. Архітектурні шари (Clean Architecture)
🚨 **Статус: Задовільно (з архітектурними боргами)**

Система має чіткий поділ на `Controllers` -> `Services` -> `Repositories`, що є хорошим фундаментом. Однак спостерігається розмиття відповідальності:

*   **Fat Services:** `TransactionService` перевантажений логікою (робота з файлами, JPEG-енкодинг, логіка активів). Це ускладнює тестування та порушує SRP (Single Responsibility Principle).
*   **Variable Shadowing:** У `TransactionRepository.Create` та `Update` часто використовуються короткі імена змінних (наприклад, `txDB` замість `tx`), що може призвести до плутанини з об'єктом транзакції GORM та самою сутністю `Transaction`.
*   **Витік логіки БД у Сервіси:** `MonobankService` безпосередньо використовує `s.db.Where(...)`. Логіка запитів має бути прихована в `Repositories`.

**Рекомендація (До/Після):**
Винести роботу з файлами в окремий `StorageService`.

```go
// ДО (у TransactionService)
func (s *txService) saveFile(fileHeader *multipart.FileHeader, folder string) (string, error) { ... }

// ПІСЛЯ (Інверсія залежностей)
type StorageService interface {
    SaveImage(file *multipart.FileHeader, folder string) (string, error)
}
// Тепер TransactionService залежить від інтерфейсу, а не від os.MkdirAll
```

### 2. Транзакційність (ACID)
🚨 **Статус: Ризиковано**

Фінансові операції використовують блоки `txDB.Transaction`, що добре. Але є критична вразливість:

*   **Race Conditions у Сервісах:** Перевірки (наприклад, чи не є рахунок синхронізованим) виконуються *до* відкриття транзакції в репозиторії.
*   **Атомарність балансу:** Використання `gorm.Expr("balance + ?", change)` — це **чудове рішення**, яке запобігає "lost updates" на рівні бази даних.

**🚨 Критична помилка:** У `MonobankService.Sync` статус синхронізації (`currentSyncStatus`) є **глобальною змінною**. В багатокористувацькому середовищі всі користувачі бачитимуть прогрес останнього, хто запустив синхронізацію.

---

### 3. Готовність до Local-First синхронізації
🚨 **Статус: Потребує доопрацювання**

*   **UUID:** Використання `string` (UUID) для ID — це **величезний плюс**. Це дозволяє клієнту генерувати ID в офлайні без ризику колізій при завантаженні на сервер.
*   **Відсутність версіонування:** Поточна модель `Base` має `UpdatedAt`, але для Local-First (особливо для вирішення конфліктів) цього замало.
*   **М'яке видалення (Soft Delete):** Реалізовано через `DeletedAt *int64`, що критично для синхронізації видалених записів.

**Що додати до моделей:**
1.  **`Version int64`**: Інкрементальний лічильник або Lamport Timestamp.
2.  **`LastSyncedAt int64`**: Час останньої успішної синхронізації конкретного об'єкта.
3.  **`ClientUpdatedAt int64`**: Час зміни на боці клієнта (для стратегії "Last Write Wins").

---

### 4. Стабільність інтеграції з Monobank
🚨 **Статус: Потребує рефакторингу (Відсутність Webhooks)**

Аналіз коду показав, що **реальних вебхуків немає**. Система використовує **Polling** (опитування):
1.  Ручний запуск `Sync` через контролер.
2.  Планувальник `startSchedulers`, який о 03:00 обходить всі акаунти.

**Ризики:**
*   **Блокування горутин:** `time.Sleep(61 * time.Second)` всередині циклу синхронізації при масштабуванні на 100+ користувачів призведе до сотень сплячих горутин, що марно споживають пам'ять.
*   **Втрата даних:** При великих паузах між опитуваннями (раз на добу) можна пропустити ліміти API по кількості транзакцій в одному запиті.

**Порада:** Для PWA Local-First важливо додати реальний Webhook-ендпоінт. Monobank надсилатиме транзакції миттєво, а бекенд через WebSockets (який у вас вже є `ws_hub.go`) повідомить фронтенд про зміну.

### 5. Тестованість (Testing Readiness)
✅ **Статус: Високий потенціал**

Завдяки використанню інтерфейсів для сервісів та репозиторіїв, код готовий до Unit-тестування.

**Проблеми:**
*   Багато функцій приймають `*models.User` як аргумент. Краще передавати конкретні `UserID` та `FamilyID`, щоб не мокати весь об'єкт користувача в тестах.
*   Пряма залежність від `time.Now()` та `uuid.NewString()` всередині методів робить результати непередбачуваними.

**Рекомендація:**
Використовуйте `Clock` інтерфейс для мокання часу в тестах.
